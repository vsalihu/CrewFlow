# Decisions

Records architecture choices, deviations from the build plan and the development defaults in use. Each entry says what was decided, why and what would change it. "Proposed default" items are configurable and are **not** company policy.

## System ownership (confirmed vs open)

| Area                                                                           | Owner today                   | Status                                                           |
| ------------------------------------------------------------------------------ | ----------------------------- | ---------------------------------------------------------------- |
| Operational demand, revisions, assignments, transport, communications evidence | CDS Operations                | Built (synthetic)                                                |
| Official bookings, profiles, compliance fields                                 | JoinedUp                      | Manual entry/verification queue only. API access unknown (open). |
| Pay, tax, P45                                                                  | Payroll system                | Out of scope; case tracking later (P3)                           |
| Identity of staff users                                                        | Supabase Auth                 | Integrated in code, not provisioned                              |
| Work-eligibility decisions                                                     | Authorised compliance officer | Recorded as readiness checks with evidence; never inferred       |

Production gates: no real data until retention, residency and provider-processing policies are approved; no live integrations until the provider capabilities are proven on the actual accounts.

## Architecture decisions

| #   | Decision                                                                                                                                                                                                                                                                                          | Reason / trade-off                                                                                                                                                                                                                                                                    |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | Modular monolith: one Next.js web app, one Node worker, shared TypeScript domain packages, PostgreSQL                                                                                                                                                                                             | As specified (§15). Business rules live only in `packages/domain`; route handlers and server actions are thin.                                                                                                                                                                        |
| D2  | Drizzle schema is the source of truth for table shape; `drizzle-kit generate` produces DDL that is reviewed and committed; RLS, grants, exclusion constraints and security-definer functions are hand-written SQL migrations                                                                      | Typed access plus explicit SQL where Drizzle cannot express it. The extension header in `0000_init.sql` was added by hand. Tables created only in custom migrations (e.g. `worker_heartbeats`) are deliberately kept out of `schema.ts` so a later `generate` does not recreate them. |
| D3  | Runtime role `cds_app` (NOLOGIN in migrations; LOGIN and password set per environment), no BYPASSRLS, no table ownership                                                                                                                                                                          | Plan §21.1. Owner credentials are used only by the migration workflow and the local seed script.                                                                                                                                                                                      |
| D4  | RLS context set with `set_config(..., true)` inside every transaction (`withContext`)                                                                                                                                                                                                             | Transaction-local, so it cannot leak to the next pooled request (tested, AT43).                                                                                                                                                                                                       |
| D5  | Child tables (revisions, stops, passengers, acceptances, responses, transport requirements) use a parent-visibility policy (`EXISTS` on the parent, which has its own branch policy)                                                                                                              | Branch isolation without duplicating `branch_id` everywhere.                                                                                                                                                                                                                          |
| D6  | Append-only via grants: runtime role has INSERT/SELECT only on audit events, order revisions, source links, worker responses and trip revision/stop/passenger/acceptance tables; no DELETE anywhere                                                                                               | Immutable evidence enforced by the database, not just code.                                                                                                                                                                                                                           |
| D7  | Composite foreign keys `(organisation_id, id)` on core relations                                                                                                                                                                                                                                  | Cross-organisation references are impossible even for the owner (tested).                                                                                                                                                                                                             |
| D8  | Worker, driver and vehicle time reservations in one table with a `tstzrange` exclusion constraint                                                                                                                                                                                                 | Concurrent incompatible bookings fail in the database (AT22). Driving reservations use the driver resource; a driver's own work uses the worker resource, and journey validation checks the two together, so a driver travelling to their own shift is not a false clash.             |
| D9  | Line versions: a material change (date, site, location, role, skill, arrival/start/end, timezone) increments `line_version`; worker acceptance and messages bind to it                                                                                                                            | Simple, explicit reconfirmation rule (AT17). Count/notes changes do not force reconfirmation.                                                                                                                                                                                         |
| D10 | Amendments require a server-issued impact token (HMAC of order, version, input hash, expiry; signed with `APP_SECRET`)                                                                                                                                                                            | Prevents saving an old preview against a changed order (§17.2).                                                                                                                                                                                                                       |
| D11 | Assignments require an agency-accepted quantity and a resolved start time                                                                                                                                                                                                                         | Capacity is measured against acceptance (§6); a reservation needs an interval. Saving an incomplete request is still allowed.                                                                                                                                                         |
| D12 | Unknown end time reserves a provisional 10 hours (configurable `provisionalShiftHours`) flagged uncertain                                                                                                                                                                                         | §7.3. Never a zero-length booking.                                                                                                                                                                                                                                                    |
| D13 | Trip capacity is enforced when each revision is written (under the trip lock), and again at publication; unknown capacity blocks publication                                                                                                                                                      | Makes the last-seat race (AT44) fail with `CAPACITY_EXCEEDED` rather than only at publish.                                                                                                                                                                                            |
| D14 | Transactional outbox: a polling loop (5 s) in the worker processes events; pg-boss runs scheduled maintenance (stuck-event release every 5 min, heartbeat every minute)                                                                                                                           | Outbox latency matters for operations; pg-boss schedules are minute-granular. A provider call is preceded by writing `delivery_unknown`, so a crash or timeout never leads to a blind resend (AT45/AT47).                                                                             |
| D15 | pg-boss runs as `cds_app` in a dedicated `pgboss` schema owned by that role (migration 0002)                                                                                                                                                                                                      | No database-wide CREATE privilege or owner credentials for the worker.                                                                                                                                                                                                                |
| D16 | Server actions for screens and JSON route handlers for `/api/v1`, both calling the same domain services                                                                                                                                                                                           | Progressive-enhancement forms with little client JavaScript. API is available for integrations and future portals.                                                                                                                                                                    |
| D17 | Development-only synthetic sign-in (`DEV_AUTH=true`, refused when `APP_ENV` is staging/production by startup validation)                                                                                                                                                                          | Supabase is not provisioned. Production identity uses Supabase `getClaims()` server-side; roles always come from the database.                                                                                                                                                        |
| D18 | Messaging is manual only; `queueProviderSend` refuses with `INTEGRATION_DISABLED` unless the WhatsApp integration status is `connected`/`sandbox`. The sandbox adapter is test-only                                                                                                               | §19.4: no unofficial automation, no simulated success.                                                                                                                                                                                                                                |
| D19 | UI primitives are small owned components (`apps/web/components/ui.tsx`) styled with Tailwind v4 tokens, instead of generating shadcn/ui components                                                                                                                                                | Same "own the code" principle as shadcn with less surface while screens settle. Adopting shadcn components later is compatible.                                                                                                                                                       |
| D20 | TanStack Table and React Hook Form are not used yet                                                                                                                                                                                                                                               | Tables are server-rendered and small; forms are server actions validated by the shared Zod schemas. Revisit when board filtering, sorting or pagination is needed (§22.5).                                                                                                            |
| D21 | Readiness: requirements have scope (worker, worker_site, site, client) and policy (blocking, warning, not_required). Only a `cleared` check valid on the work date satisfies a requirement                                                                                                        | No legal conclusions inferred from chat. Coordinators cannot approve readiness (capability).                                                                                                                                                                                          |
| D22 | Late-order urgency uses time to earliest arrival: >12 h normal, 2–12 h late, <2 h urgent (proposed defaults in `policy.ts`, overridable per organisation/branch settings)                                                                                                                         | §5.4. A task goes to whoever is on duty; with nobody on duty an urgent order raises an unowned coverage alert.                                                                                                                                                                        |
| D23 | TypeScript 6.0.3 (not 7.x)                                                                                                                                                                                                                                                                        | typescript-eslint 8.71 supports `<6.1`. Revisit when the lint toolchain supports TypeScript 7.                                                                                                                                                                                        |
| D24 | Node 24 LTS is the deployment target (`.nvmrc`, Docker); code and tests also run on Node 22.12+                                                                                                                                                                                                   | The build container here had Node 22; engines allow both.                                                                                                                                                                                                                             |
| D25 | PostgreSQL 17 in CI to match current Supabase projects; developed and tested locally on 16.15                                                                                                                                                                                                     | Uses only features available in both (btree_gist, pg_trgm, pgcrypto, range exclusion). Confirm the managed project's major version before production.                                                                                                                                 |
| D26 | Docker images split into `docker/web.Dockerfile` and `docker/worker.Dockerfile`; optional `npm_ca` build secret for TLS-intercepting proxies                                                                                                                                                      | Render builds one Dockerfile per service. Both images were built and run against PostgreSQL.                                                                                                                                                                                          |
| D27 | Migrations run from a protected GitHub Actions workflow, not as a Render pre-deploy command                                                                                                                                                                                                       | Keeps owner credentials off the runtime services (§21.1).                                                                                                                                                                                                                             |
| D28 | One site-entrance rule (`locationProblem`) used by line readiness, booking drafts, manifests and journey validation: the entrance must belong to the line's site, be verified and be valid on the work date                                                                                       | Previously each check looked only at `verified_at`, so an expired entrance or one from another site could be sent. A site change now clears the old entrance instead of carrying it over.                                                                                             |
| D29 | A departed trip cannot be revised; changes after departure go through disruptions. Any manifest change (revision or added passenger) supersedes unsent manifests, asks the driver to reconfirm and reopens the transport need of anyone removed                                                   | A removed passenger previously stayed marked as covered by the trip; an added passenger did not invalidate a manifest already drafted.                                                                                                                                                |
| D30 | Open source conflicts are checked again when a trip is published, a manifest is drafted and a send is recorded, not only when the order is accepted                                                                                                                                               | A conflict raised after a draft was made could otherwise be sent as if settled.                                                                                                                                                                                                       |
| D31 | Attendance is recorded as revisioned segments (`attendance_segments`); corrections and voids add a revision and keep the old one. Hours are approved per timesheet by someone other than the person who entered it, and review items need a written justification                                 | Separation of duties for pay; the original timesheet text is kept as a `timesheet` source message.                                                                                                                                                                                    |
| D32 | Break rules are versioned per client (optionally per site) with an agreement reference and set only with `policy.manage`. With no rule the unpaid break must be entered from the timesheet; no default break is invented                                                                          | Break terms are contractual and unknown for most clients (§28).                                                                                                                                                                                                                       |
| D33 | Payroll exports are CSV files stored in the database with a SHA-256 checksum, created under a branch advisory lock, and never regenerated. The runtime role can update only the acknowledgement columns. Changes after export go out as reversal plus new hours rows in a later correction export | Payroll must be able to reconcile every file it imported; there is no agreed payroll file layout or upload integration, so download and import stay manual.                                                                                                                           |
| D34 | CrewFlow branding was requested but no branding change existed in the repository; the product name stays “CDS Operations” until a naming decision is made                                                                                                                                         | The local changes described for this round (journey safety, site entrances, conflict checks, branding) were not present in the working tree, so the existing code in those areas was reviewed instead.                                                                                |

## Known gaps

- No name-correction or identity-review workflow yet (AT23).
- Contact-change propagation tasks (JoinedUp/payroll) are not generated (AT41 covers draft safety only).
- No OpenAPI document is generated yet; schemas are shared Zod objects in `@cds/contracts`.
- Rate limiting and MFA enforcement depend on Supabase/hosting configuration and are not yet in place.
- Branch and organisation settings (urgency thresholds, buffers) have no settings screen; they are JSON on `organisations.settings`/`branches.settings`.
- Timesheets are typed in from the message or photo; photo/file upload and storage are not built.
- The payroll CSV layout is a working format, not one agreed with a payroll provider; weekly totals, overtime and pay rates are not calculated.
- Approved hours are not compared with JoinedUp records (AT31).
